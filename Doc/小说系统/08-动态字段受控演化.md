# 08 · 动态字段受控演化

> 本卷回答「AI 自己造字段会不会失控」。结论：**「定义收口、值自由发挥」**——字段的**登记与约束**必须收紧（登记、类型、枚举、别名、门禁、转义、上限），字段的**取值**继续让 AI 自由发挥。当前实现的脆弱点不在「让 AI 发挥」，而在「发挥出来的字段没人管」。

## 0. 本卷范围与不做什么

**范围**

- 字段定义（`field_defs`）的登记、类型/枚举校验、Canon 门禁。
- 字段值（`entity_fields`）的写入校验、归一、序列化转义。
- `layer`（多面身份）的枚举化与读取默认策略。
- 读取侧的数量上限与分页。
- 脏数据清理与迁移。

**不做**

- 不定义整体数据模型 → `01`。
- 不定义 `FieldDef` / `EntityField` 契约字段 → `02` §2.12。
- 不定义校验器框架 → `06`。
- 不定义提交事务 → `07`。

## 1. 现有落点

### 1.3 一个**确定性缺陷**（与 AI 可靠性无关）

```cpp
// NovelFields.cpp:290-292
arr += fmt::format(
    R"({{"key":"{}","value":"{}","value_json":{},"layer":"{}","chapter_scope":{},"note":"{}"}})",
    f.field_key, f.value_text, f.value_json, f.layer, f.chapter_scope, f.note);
```

- `value_text` 与 `note` 由 AI 自由填写，**含 `"` 或换行即产出非法 JSON**。
- 同一文件的 `Esc`（`:50-61`）**只转义 SQL 单引号**，不是 JSON 转义。
- 该函数的输出被 `NovelMcpTools.cpp:409-412` 作为 `dynamic_fields` 嵌进 `novel_get_entity` 的返回，**直接喂给 Agent**。
- 现成可复用的转义助手：`src/novel/NovelImageGen.cpp:34 JsonQuote`（用 `yyjson_mut_val_write`）。

### 1.4 MCP 侧

- `novel_upsert_field_def`（`NovelMcpTools.cpp:1100`）、`novel_list_field_defs`（`:931`）、`novel_list_entity_fields`（`:943`）、`novel_upsert_entity_field`（`:1136`）。
- 写入受 `mcpAllowWrite` / `SHINE_MCP_ALLOW_WRITE` 控制（`:828-830`）；`UpsertEntityField` 后有 `RedisDel`（`:515`）。
- `MyCin`：`AgentKit::RegisterToolsFor` 在写开关开启时给 `field_builder` 授予 `upsert_field_def`（`AgentKit.cpp:870-874`）。

### 1.5 缓存

- `novel:cache:entity:<id>`（TTL 60s）在 `novel_upsert_entity_field` 后有 `RedisDel`（`:515`）；但 `RedisGet` **无调用点**，缓存实际不生效。

## 2. 目标设计

### 2.1 边界原则

| 层 | 自由度 | 理由 |
|---|---|---|
| **定义（`field_defs`）** | **收口**：必须登记、有类型、可枚举、走门禁 | 定义是「契约」，契约一旦漂移，全系统的机器校验都失效 |
| **值（`entity_fields`）** | **自由**：AI 可以在已登记字段上自由填写内容 | 这是「不写死小说体系」的价值所在 |

> **一句话**：AI 的自由度只在「值」这一层。**不允许 AI 定义出未登记的键并直接写值。**

### 2.2 写入校验（三步，全部必做）

`UpsertEntityField` 的执行顺序改为：

```
① 归一化
   field_key ← NormalizeKey(field_key)
     - 去首尾空白
     - 转小写
     - 空白与连字符 → 下划线
     - 命中别名表 → 替换为规范键（§2.4）
   若不满足 ^[a-z][a-z0-9_]{1,39}$ → 拒绝（code=contract）

② 查定义
   查 field_defs(scope, entity_kind, field_key)
     - 未命中 → 拒绝（code=field_unregistered），并把该提案写入 field_defs 的 PROPOSED（§2.3）
     - 命中且 status='PROPOSED' → 允许写入，但记 note='unapproved_field'
     - 命中且 status='CANON' → 正常放行

③ 校值（按 value_type）
   text   : 长度 ≤ 4096 字符；禁止控制字符（除 \n）
   number : from_chars 解析成功；若 description 中声明区间则须落在区间内
   json   : yyjson_read 解析成功且为对象/数组（不允许裸标量）
   enum   : 必须命中 enum_json 的某一项（区分大小写）
   任一步失败 → 拒绝（code=validate），错误信息含字段名与期望类型
```

**拒绝即失败**（不改默认、不静默纠正），符合 `07` §2.6 的「不允许静默修正」原则。

### 2.3 字段定义的 Canon 门禁

**问题**：当前 `UpsertFieldDef` 只有 `is_system` 一个标记，非系统字段一路直写（`NovelFields.cpp:97-128`），**AI 随时能新增字段**。

**目标**：

| 项 | 决定 |
|---|---|
| 新增列 | `field_defs.status ∈ {PROPOSED, CANON}`（`02` §2.12 已定为契约字段） |
| 写入 | AI/Agent 的提案一律写 `PROPOSED`；`is_system=1` 的种子字段写 `CANON` |
| 人工路径 | UI 可手工升 `CANON`（与 `canon_logs` 同样的交互模式） |
| **自动升格规则**（无人值守必需） | 在 `09` §2.5 的检查点（默认每 10 章）执行：某 `PROPOSED` 字段若满足**全部**条件 → 自动升 `CANON`：<br>① 已出现 ≥ 5 次；<br>② 值类型始终一致；<br>③ 无同义键冲突（§2.4）；<br>④ 最近 3 章内仍在使用 |
| 拒绝 | 不满足则保持 `PROPOSED`，并写入人工复核清单 |
| 硬上限 | 单个工程 `field_defs` 条数上限（默认 500）；超限时**新增被拒**并进复核清单（防止无界膨胀） |
| 删除 | 删除 `CANON` 字段需 `force`（沿用 `DeleteFieldDef:168-180` 的既有语义） |

**与不变式 I12 的关系**：I12 是「写入前必须已登记」——`PROPOSED` 也算已登记（只是未人审）。这样既保证机器可校验，又不阻塞 AI 发挥。

### 2.4 归一与别名

| 机制 | 内容 |
|---|---|
| 归一函数 | `NormalizeKey`：trim → lower → 空白/连字符转下划线（§2.2 ①） |
| 别名表 | 新增 `field_aliases(alias TEXT PRIMARY KEY, canonical_key TEXT, note TEXT)`；读取与写入**都**先过别名表 |
| 冲突检测 | 若两个规范键语义重叠（如 `emotion` 与 `mood`），在检查点产出「疑似同义」清单，等人裁定；**不自动合并** |
| 禁止 | 禁止在同一个 `(scope, entity_kind)` 下建语义重复的键；`field_defs` 唯一索引已防同键，但语义重复需靠 §2.3 的自动升格条件③ |

**为什么必须有别名**：现有 `idx_field_defs_key`（`:30`）与 `idx_ef_uniq`（`:46-47`）都是**大小写敏感**的字符串比较，`Emotion` 与 `emotion` 会被当作两个字段。几百章后必然分裂。

### 2.5 序列化转义（修确定性缺陷）

| 项 | 决定 |
|---|---|
| 目标 | `EntityFieldsJson` 输出的必须是**合法 JSON**（可被 `yyjson_read` 解析） |
| 方案 A（推荐） | 用 `yyjson_mut_doc` 构造数组与对象，`yyjson_mut_val_write` 序列化 |
| 方案 B（最小改动） | 复用 `NovelImageGen.cpp:34` 的 `JsonQuote`（内部用 `yyjson_mut_strncpy` + `yyjson_mut_val_write`）对 `field_key`/`value_text`/`layer`/`note` 逐个转义；`value_json` 先 `yyjson_read` 校验再原样嵌入（非法则退化为 `null`） |
| 验收 | 单元级：写入 `value_text = 他说"你好"\n第二行` 后，`EntityFieldsJson` 的输出能被 `yyjson_read` 成功解析，且还原出原字符串 |
| 附带要求 | `note` 字段同样转义；`created_by` 不进 JSON 输出（无必要） |

**这条必须单独修**：它与架构无关，是纯粹的 bug；在无人值守下会造成「静默吞数据」。

### 2.6 `layer` 枚举化

| 项 | 决定 |
|---|---|
| 合法取值 | `global` / `public` / `mask` / `true` / `private`（对齐 `SeedBuiltinFieldDefs` 的用法与 `NovelVisual` 的 `canon_status` 命名习惯） |
| 写入校验 | 不在此集合内 → 拒绝 |
| 读取默认 | `layer` 为空参数时，读取策略为：**`global` 全取；`public` 全取；`mask`/`true`/`private` 仅当显式指定或调用方为 POV 本人时取** |
| 与 POV 的关系 | 进入 `04` 的 L3 时，`mask` 层默认不进上下文（防写穿，配合不变式 I2） |

**理由**：`layer` 现在是无枚举的自由字符串（`NovelFields.cpp:40`/`:187`），拼错即新层。多面身份是本系统很有价值的能力，但必须让「谁知道哪一面」变成可判定的事。

### 2.7 读取侧限制

| 项 | 决定 |
|---|---|
| `ListEntityFields` | 加 `limit`（默认 **50**，最大 200）与 `offset`；`ORDER BY field_key, chapter_scope DESC, layer`（沿用现有排序，`:227`） |
| `ListFieldDefs` | 加 `limit`（默认 **200**） |
| `GetEntityFieldByKey` | 改为按唯一索引直接查 `(entity_id, field_key, chapter_scope, layer)`，不再走全表后线性搜索（`:244-257`） |
| 进入上下文 | 单个实体的动态字段进入 `04` 的 L3 时，按 `04` §2.3 的 `S(c)` 打分**裁剪到前 K 条**（K 由 `09` §2.4 定） |
| 超限行为 | 超 `limit` 时返回截断标记（`truncated:true` + `total`），**不静默截断** |

### 2.8 脏数据清理与迁移

上线 §2.2 的校验后，历史数据可能不合规。迁移步骤：

| 步 | 内容 |
|---|---|
| 1 | 扫描 `entity_fields`，列出**无对应 `field_defs`** 的 `field_key` → 批量生成 `PROPOSED` 定义（保留数据，不删） |
| 2 | 扫描 `field_key`，列出**不满足 `^[a-z][a-z0-9_]{1,39}$`** 的 → 按 `NormalizeKey` 归一；归一后冲突的进人工清单 |
| 3 | 扫描 `layer`，列出不在枚举内的 → 统一改为 `global` 并记 `note` |
| 4 | 对 `value_type=json` 的已有值，用 `yyjson_read` 抽查，非法者标 `note='invalid_json_legacy'` |
| 5 | 迁移全程写入 `audit_logs`（`actor='migration'`） |

## 4. 验收判据
