# 01 · 世界状态与数据模型

> 本卷是全集**唯一的实体与字段定义处**：世界状态由哪些实体构成、每个实体有哪些字段、存在哪张表、当前态与历史态如何分离、以及「第 N 章时某实体是什么状态」这类时间语义的规范查询方式。其余各卷引用本卷，不得重复定义。

## 0. 本卷范围与不做什么

**范围**

- 定义全部实体、字段、表、索引、外键语义与时间语义。
- 定义「当前态 / 历史态 / 快照」三种存储形态及其查询方式。
- 给出「表 → C++ 结构体 → 公开 API」的覆盖矩阵（暴露实现缺口）。
- 声明视觉层与系统层表的**归属**（细则在 `11` 与 `07`）。

**不做**

- 不定义阶段间传递的 JSON 契约 → `02`。
- 不定义校验规则的具体阈值 → `06`。
- 不定义视觉 Prompt 九层细节 → `13`。
- 不定义 StateDiff 的计算算法 → `07`（本卷只定义它改了哪些实体）。

## 2. 目标设计

### 2.1 实体统一模型

一切可命名对象都是 `entities` 的一行，`kind` 决定它挂哪些详情表。这是本系统「不写死小说体系」的基础：新增叙事维度优先用动态字段（`08`），只有需要独立时间线或结构化查询时才新增表。

```
entities(kind)
 ├─ person      → entity_personas / character_arcs / character_status / emotion_events / character_knowledge / dialogue_styles
 ├─ location    → location_details（parent_id 成树）/ location_distances
 ├─ faction     → faction_details / faction_members
 ├─ item|prop|treasure|clothing → item_details；流转见 entity_ownerships
 ├─ ability     → ability_details（system_id 归属 power_system）
 ├─ event       → event_details / event_participants；因果见 causal_links
 ├─ plot        → plots / plot_beats
 ├─ secret      → secrets / secret_knowledge
 ├─ foreshadowing / mystery → foreshadowings / mysteries + mystery_beats
 └─ world_* / calendar / history / culture / … → 各自 *_details
```

**`kind` 是「元类别」，不是设定细节**

31 种 `kind` 回答的是「这个对象在故事里扮演哪一类角色」（人 / 地点 / 物品 / 能力体系 / 势力 / 事件 / 谜 …），**不是**它的世界观名字。

> 例：斗罗大陆的「魂师」是 `person`、「武魂」是 `power_system`、「魂技」是 `ability`、「魂环」是 `item` + `relations(attached_to)`、「魂兽」是 `creature`、「魂力等级」是动态字段。**一本书的设定再独特，也不需要新增 `kind`，更不需要新建表。**
> 完整映射范式与扩展规则见 §2.9「扩展机制」。

**新增约束（本集要求）**

- R1：31 种 `kind` 是**元类别**；**绝大多数设定不需要新 `kind`**——子类型用 `entity_subtype` 动态字段（`08`）表达即可。确需新增 `kind`（例如科幻要 `ship`）时**必须走 §2.9.5 的改骨架流程**，不得在代码里私自新增。
- R2：一个实体只能挂「与其 `kind` 匹配」的详情表；跨 kind 的详情表引用视为缺陷。
- R3：`entities.status` 为 `dead`/`destroyed` 后，该实体不得再出现在事件的 `actor` 角色中（不变式 I3）。
- R4：**新设定不得要求新建表**（不变式 I13）；判定用 §2.9.4 的 T1–T3。

### 2.2 当前态 / 历史态 / 快照

三种形态必须分离，**不得混用**：

| 形态 | 定义 | 存放 | 查询方式 |
|---|---|---|---|
| **当前态** | 「现在是什么状态」 | **查询派生**，不建独立表 | 见 §2.3 的规范查询 |
| **历史态** | 「过去发生过什么」 | `character_status`（按章 append）、`emotion_events`、`entity_events`、`relations(from_chapter,to_chapter)`、`character_knowledge.chapter_known` | 按 `chapter_id` 过滤 |
| **快照** | 「某一章的完整世界状态冻结副本」 | `entity_versions`（现有，零引用）；本集另要求章级快照 | 按 `(entity_id, ver)` 或章级键取 |

**关键设计决策：当前态不建表，一律由查询派生。**

理由：现有 `character_status` 是 append-only，`GetLatestCharacterStatus` 已能正确派生「截至第 N 章」的状态（见 §2.3.2）。若再维护一张 `current_state` 表，就出现了两个真相源——这正是旧文档「Current 与 History 混在一起」的另一种失败方式。

**代价与缓解**：查询派生需要索引支撑。现有 `idx_cstat_entity` / `idx_cstat_ch` 已具备；当单实体状态行数超过阈值（见 `09` §2.4）时，再引入物化视图并按 Commit 时机刷新。

### 2.3 时间语义

#### 2.3.1 四层时间轴（对应不变式 I6）

| 层 | 字段 | 语义 |
|---|---|---|
| 世界历 | `calendar_eras` + `calendar_seasons` + 各表的 `time_label` | `time_label` 是**自由文本**，必须与 `calendar_eras` 对齐；不做机器解析 |
| 叙事序 | `volumes.ord` → `chapters.ord` → `scenes.ord` → `plot_beats.ord` | 严格递增；**一切「第 N 章」都指 `chapters.ord`** |
| 人生 | `character_arcs` + `character_status.chapter_id` | 角色成长阶段与逐章状态 |
| 移动 | `location_distances.days_estimate` + 事件/状态上的 `location_id` | 旅行耗时校验的依据 |

#### 2.3.2 规范查询：「第 N 章时某实体是什么状态」

这是全系统最常用的查询，**唯一定义**如下：

```sql
-- 截至第 N 章（含）的人物状态
SELECT * FROM character_status
WHERE entity_id = :id AND chapter_id <= :N
ORDER BY chapter_id DESC, id DESC
LIMIT 1;
```

实现：`NovelGraph.cpp:288-318`。语义：

- `chapter_id = :N` 取「`chapter_id` 最大、同章 `id` 最大」的一条，即**第 N 章结束时**的状态。
- `:N = 0` 表示不过滤章，取全库最新。
- 无命中 → 返回 `CharacterStatusRow{.entity_id=:id}` 空壳（**不报错**，调用方必须能处理「该角色暂无状态」）。

同类查询的推广规则（本集要求保持一致）：

| 对象 | 规范查询 |
|---|---|
| 关系是否有效 | `from_chapter <= :N AND (to_chapter = 0 OR to_chapter >= :N)` |
| 角色是否知情 | `character_knowledge.knows = 1 AND (chapter_known = 0 OR chapter_known <= :N)` |
| 角色知情的秘密 | `NovelGraph.cpp:664 GetSecretsFor(id, :N)` |
| 视觉阶段外观 | `visual_states`：`from_chapter <= :N AND (to_chapter = 0 OR to_chapter >= :N)`，取 `from_chapter DESC, ord DESC LIMIT 1`（`NovelVisual.cpp:124-171`） |
| 物品归属 | `entity_ownerships.from_chapter <= :N AND (to_chapter = 0 OR to_chapter >= :N)` |
| 伏笔状态 | 按 `setup_ch <= :N` 筛出已埋的，再按 `status` 分档 |

#### 2.3.3 伏笔状态机（对应不变式 I8）

```
PLANNED ──埋下──► PLANTED ──推进──► DEVELOPING ──揭示──► REVEALED ──收束──► RESOLVED
   │                                                                          ▲
   └──────────────── 允许直接跳到 REVEALED（短伏笔）───────────────────────────┘
```

规则：

- `status` 只能沿上述方向推进，**不得回退**（回退视为世界状态冲突，进 `07` 的冲突处理）。
- `ListOpenForeshadows`（`NovelGraph.cpp:604`）只返回 `PLANNED/PLANTED/DEVELOPING`，即「未回收」。
- `importance` 0–100，用于 Context 排序（`04`）与超期告警阈值（`06`）。

#### 2.3.4 谜团与信息节奏

`mysteries`（question / answer / status / ask_ch / answer_ch / importance）+ `mystery_beats`（`beat_type ∈ question|hint|reveal|answer|red_herring`）。

**三者的分工必须严格区分**（旧文档混用，本集修正）：

| 概念 | 回答的问题 | 存哪 |
|---|---|---|
| 伏笔 Foreshadow | 「作者打算在何时回收哪个埋点」 | `foreshadowings`（作者侧账本） |
| 谜团 Mystery | 「读者被引导成什么样，何时给答案」 | `mysteries` / `mystery_beats`（读者侧节奏） |
| 知情 Knowledge | 「这个角色此刻知道什么」 | `secret_knowledge` / `character_knowledge`（角色侧边界） |

### 2.4 时间化边与状态机

#### 2.4.1 关系类型枚举（`relations.rel_type`）

现有实现为自由字符串。本集要求收敛为固定集（扩展需登记）：

`family` `love` `friend` `ally` `enemy` `rival` `mentor` `student` `subordinate` `superior` `member_of` `owns` `counter`（能力克制，见 `ability`）`knows_secret`

每条边带 `strength` 与生效区间，**关系变化不覆盖旧行，而是关闭旧行 + 新增新行**（`to_chapter` 语义）。

#### 2.4.2 因果网

- `causal_links` 是 DAG；`NovelGraph.cpp:515` 已禁自环，**缺环检测**（见 §3）。
- `event_participants(event_id, entity_id, role)`，`role ∈ actor|victim|witness|faction|…`。
- `entity_events` = 档案履历；`causal_links` = 世界线推演边。**两者不可混用**。

#### 2.4.3 持有流转

`entity_ownerships(owner_id, item_id, from_chapter, to_chapter, how, note)`；同一物品在同一 `chapter_id` 最多一个 `owner`（不变式 I5 的物品侧）。

#### 2.4.4 事件

`event_details(entity_id, time_label, location_id, cause_note, result_note)`；`UpsertEvent` 强制 `entities.kind='event'`（`NovelGraph.cpp:492`）。

#### 2.4.5 知情

`secret_knowledge(secret_id, entity_id, knows, chapter_known)` 与 `character_knowledge(entity_id, fact_kind, fact_id, fact_text, knows, chapter_known)`。

**统一规则**：任何「角色知道某事」都必须落在这两张表之一；正文中出现角色使用未记入知情表的信息，判为不变式 I2 违反。

### 2.5 叙事结构层

```
volumes.ord ─► chapters.ord ─► scenes.ord ─► plot_beats.ord
                                    │
                          scene_cast / scene_foreshadows
```

- `scenes` 是正文链与影视化链的**唯一衔接点**（`11` §2.2 引用）。
- `scene_cast(scene_id, entity_id, role)` 决定该场「谁在场」；这是 Context 组装与视觉映射的输入。
- `scene_foreshadows(scene_id, foreshadowing_id, action)`，`action ∈ plant|develop|payoff`。
- `plots(kind, title, status, intro_ch, target_ch, note)` + `plot_beats(beat_type ∈ setup|rising|turning_point|climax|falling|resolution|revelation)`。
- **`OpenLoop` 不设实体**：查询「开放线索」= 未回收伏笔 ∪ 未解谜团 ∪ 未结剧情线（见 `00` §2.5）。

### 2.9 扩展机制：不建表也能长出魂师与魂环

> 回答一个必然会被问到的问题：**「一本小说有魂师/魂武/魂环，另一本没有，固定 schema 是不是把 AI 限死了？」**
> **结论：不限定「设定」，只固定「骨架」。** 一本小说的设定再独特，也不需要新增 `kind`，更不需要新建表。

#### 2.9.1 一条判据：骨架 vs 内容

| | 是否固定 | 例子 | 理由 |
|---|---|---|---|
| **叙事骨架** | **固定** | 人物、地点、物品、事件、因果、伏笔、秘密、知情、剧情线、章/场/镜、状态随时间变化 | **任何小说都有**。这是「故事成立的物理法则」，不是世界观 |
| **世界内容** | **自由** | 魂师、武魂、魂环、灵根、丹田、契约兽、异能等级、封号斗罗 | 一旦进表，就把小说体系写死了 |

**不变式 I1–I12 全部落在「骨架」这一侧**，因此它们对任何题材都成立。

#### 2.9.2 范式：斗罗大陆（**0 张新表、0 个新 `kind`**）

| 斗罗设定 | 落点 |
|---|---|
| 魂师 | `entities(kind='person')` + 动态字段 `entity_subtype='魂师'` |
| 武魂（蓝银草 / 昊天锤） | `entities(kind='power_system')` —— 一个武魂 = 一个实体，同名共享 |
| 魂技 | `entities(kind='ability')`，归属其武魂（`ability → power_system` 的 `system_id` 语义） |
| 魂环（最多 10 环） | `entities(kind='item')` + `relations(rel_type='attached_to')` 挂到武魂；年限用动态字段 `ring_age_years(number)` |
| 魂骨 | `entities(kind='treasure')` |
| 魂兽 | `entities(kind='creature')` |
| 魂导器 | `entities(kind='item')`（或 `tech`） |
| 唐门 / 史莱克学院 | `entities(kind='faction')` |
| 魂力等级（91–99 封号斗罗） | 动态字段 `soul_level(number)` + `author_rules` 一条「等级只升不降」 |
| 武魂克制 | `relations(rel_type='counter')`（§2.4.1 已有） |
| 魂师大赛 | `entities(kind='event')` + `causal_links` |

换题材同样成立：灵根 → `ability`；丹田 → 动态字段；契约兽 → `creature`；异能等级 → 动态字段。

#### 2.9.3 三个扩展点（都不建表）

| # | 扩展点 | 能表达什么 | 依赖 |
|---|---|---|---|
| **E1** | **`entity_subtype` 动态字段**（`08` 种子第 12 条） | 任意子类型命名：`魂师` / `魂兽` / `灵根持有者` / `封号斗罗` | `08` 的登记与归一 |
| **E2** | **`power_system` + `ability` + `relations`** | 任意能力体系：境界、年限、附着力、克制、升级路径 | §2.4.1 的关系枚举 + §2.6 |
| **E3** | **动态字段 + `layer`** | 任意设定维度 + 多面身份（公开身份 vs 真实血脉） | `08` |

**三者组合可覆盖「异世界体系」的绝大多数需求。**

#### 2.9.4 何时才**真的**该建表（T1–T3，须全满足）

| 判据 | 含义 |
|---|---|
| **T1 跨实体聚合** | 需要 `SELECT … GROUP BY` 类统计（如「全部封号斗罗的平均魂力」）。动态字段做不到高效聚合 |
| **T2 参与机器校验** | 是某条不变式 / 校验项（`06` §2.3）的**数据来源**。正例：`location_distances` 是 K18 旅行时间的唯一来源，所以它必须存在 |
| **T3 有独立生命周期** | 需要自己的时间线 / 版本 / 状态机。正例：`character_status` 的按章 append |

- 只满足 1 条 → 用**「通用结构 + 索引」**（`entity_fields` 的 `idx_ef_key` 已能按 `field_key` 查）
- **三条全满足** → 才考虑建表，且必须走 §2.9.5

> 按此判据，**魂环 / 武魂 / 魂技 / 魂力等级一条都不满足**，因此本来就不该为它们建表。

#### 2.9.5 改骨架流程（确需新增 `kind` 或表时）

**必须同时完成四件事，缺一不可**：

1. 修订 §1.1.2 的 `kind` 表（或 §1.2 的表清单），并在 §3 记录原因；
2. 同步更新 §2.8 覆盖矩阵（**新增表必须立刻给出 P0/P1/P2/P3 定级**）；
3. 补 `06` §2.3 的校验项（新 `kind` 至少要被 K26 之外的规则覆盖）；
4. 评估对 `04` 检索算法、`02` 契约枚举、以及 **19 个 MCP 查询工具**的影响（工具是按骨架参数化的，**改骨架 = 改工具契约**）。

**禁止**：在代码里私自新增 `kind` 或表而不改文档——这正是 G17「表与实现脱节」的成因。

#### 2.9.6 「不乱来」的四道闸

| 闸 | 位置 | 作用 |
|---|---|---|
| **登记** | `08`（`field_defs`，`PROPOSED → CANON`） | 没登记的 `field_key` 写不进去 |
| **类型 / 枚举** | `06` K14 / K15 | 值必须符合 `value_type` / `enum_json` |
| **审计** | `canon_logs` + `audit_logs` | 谁在什么时候造了什么 |
| **可回滚** | `07` §2.4 快照 | 造错了能退回去 |

> **自由在「能造什么」，约束在「造出来的必须被登记、命名、类型化、可校验」。**
> AI 可以造出「魂环年限」这个字段，但它必须是 snake_case、必须有类型、必须进登记表、必须能被校验——而不是天马行空地写一个没人认识的键。

#### 2.9.7 「能用通用结构就别建表」的真正理由

**先纠正一个容易说绝对的说法**：不是「每书一套表 → 每书一套工具」这么粗。真正的机制是「**扩展位置决定工具是否要改**」：

| 扩展位置 | 现有工具要不要改 | 为什么 |
|---|---|---|
| 往 `entity_fields` 加字段（E1 / E3） | **不用改** | `novel_get_entity(id)` 原样返回 `dynamic_fields`；`novel_list_entity_fields(entity_id, chapter_id, layer)` 按参数取任意字段 |
| 加 `entity_subtype` 子类型 | **不用改** | `novel_list_entities(kind=…)` 按 `kind` 参数化，**子类型是数据不是结构** |
| 用 `relations` 加新关系类型（E2） | **不用改** | `novel_get_relations(entity_id)` 原样返回 `rel_type` |
| **新建一张表** | **要改** | 没有任何现有工具知道这张表 |

**「传参数就能复用」成立的前提**：参数是**数据**（`entity_id` / `field_key` / `kind` / `layer` / `chapter_id`），不是**结构**（表名 / 列名）。**这正是本系统把全部扩展收在 `entities` + `entity_fields` + `relations` 三张通用表里的原因**——换成「每书一张表」，参数就不再是数据、而是结构了。

**新建表的四层代价**（按隐蔽程度排序）：

| # | 代价 | 说明 |
|---|---|---|
| 1 | **静默少给数据（最危险）** | 工具照样能调用、**不报错**，只是看不见新表的内容。无人值守下就是静默劣化（与 `04` §2.4 的「降级必须可见」同源问题） |
| 2 | **切片语义要按书重定义** | `GetCharacterSlice` 是一次 JOIN 的结果；新表要不要进这个 JOIN、按什么条件进，每本书都不同 |
| 3 | **四道闸随之失效** | `chapter_scope` / `layer` 过滤、`value_type` 校验、`field_aliases` 归一，全是为 `entity_fields` 设计的；裸表查询绕不过去、也管不到 |
| 4 | **不变式无法统一过滤** | I2（POV 知情边界）要求系统**自动**挡掉不该看的；通用表查询不知道该挡什么 |

**边界（本集规定）**：

- **允许**「按**字段**参数化」的半通用查询——已实现的 `novel_list_entity_fields(entity_id, chapter_id, layer)`、`novel_list_entities(kind, filter, limit)`、`novel_get_relations(entity_id)` 都是这一类。它们**跨书复用**，且保留四道闸。
- **禁止**「按**表名 / SQL** 参数化」的通用查询（如 `novel_query_table(table, where)`）。它形式上能复用，实际把「受控」变成「不受控」——**而「受控」正是本系统相对「一股脑塞 Prompt」的全部价值**。

**结论**：能表达在 `entities` + `entity_fields` + `relations` 里的，一律不建表；一旦建表，就要同时接受上面四层代价，并走 §2.9.5 的流程。
