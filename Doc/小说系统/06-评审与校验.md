# 06 · 评审与校验

> 本卷把旧文档中「检查剧情/人物/因果/节奏」这类主观清单，拆成两类：**可机器校验的**（必须由代码断言）与**需语义判断的**（交给 LLM 并给 rubric）。这是无人值守能否成立的关键——凡是能算的，不许问 LLM。

## 0. 本卷范围与不做什么

**范围**

- 两类校验的分工原则与判定流程。
- Issue 类型表（供 `02` §2.6 的 `Issue.type` 引用）。
- **机器校验项清单**（编号、断言、数据来源、阈值）。
- 语义评审 rubric（维度、评分、阈值）。
- 四层评审的差异（**已移除生成评审**）。
- 失败后的修复路径与回执要求。
- 评审器自身的可信度保障（防「自评全 PASS」）。

**不做**

- 不定义契约字段 → `02`。
- 不定义阶段顺序 → `03`。
- 不写评审 Prompt 全文 → `05` §2.1。
- 不定义 StateDiff 的组装 → `07`。

## 2. 目标设计

### 2.1 两类校验的分工（唯一裁决规则）

> **凡是能用代码判定的，禁止交给 LLM。**

| 类别 | 判定者 | 输出 | 失败后果 |
|---|---|---|---|
| **机器校验** | 校验器（纯代码） | `ValidationReport{check_id, pass, detail}` | 直接 `code=validate`，回到产出该对象的阶段（`03` §2.6） |
| **语义评审** | LLM（`review` Agent） | `ReviewVerdict`（`02` §2.6） | 进入 `CHAPTER_REPAIR` |

**判定归属的裁决规则**（防止把机器活推给 LLM）：

| 问题形态 | 归属 |
|---|---|
| 涉及「存在性 / 数值 / 集合运算 / 时间序 / 唯一性 / 边界」 | **机器** |
| 涉及「合理性 / 文风 / 节奏 / 情绪 / 意图」 | 语义 |
| 两者都有 | 拆两条：机器判可判定部分，LLM 判其余 |

**硬性要求**：`ReviewVerdict.issues[].machine_checkable=true` 的条目，**必须同时能被机器校验项发现**。这是校验器覆盖率指标。

### 2.4 语义评审 rubric

`review` Agent 按维度打分（0–100），全部维度与阈值如下：

| 维度 | 考察 | 阈值（低于此值判 `FAIL`） |
|---|---|---|
| `plot` | 本章目标是否达成；是否推进了声明的剧情线 | 60 |
| `character` | 言行是否符合人设、状态、目标 | 60 |
| `causality` | 事件是否由前置事件驱动；有无无因之果 | 60 |
| `world` | 是否违反世界规则与作者硬规则 | **80**（世界观错一次即不可接受） |
| `timeline` | 时间描述是否自洽 | 70 |
| `foreshadow` | 埋点/推进/回收是否符合计划 | 60 |
| `pacing` | 节奏是否与 `EmotionalGoal` 一致 | 50 |
| `style` | 文风是否漂移 | 50 |

**总判定**：

```
verdict = FAIL  if  任一维度 < 其阈值
               or  存在 severity=high 的 issue
               or  issues 中存在 machine_checkable=true 的条目（说明校验器漏了，必须先修校验器）
         else PASS
```

**`world` 维度阈值 80、且「任一 high issue 即 FAIL」是本 rubric 与旧文档最大的区别**：旧文档只列检查项，无阈值，等于没有判据。

### 2.5 四层评审

| 层 | `target_type` | 判定重点 | 机器项 |
|---|---|---|---|
| 章节 | `chapter` | plot / character / causality / world / timeline / foreshadow / pacing / style | K01–K08、K10–K12、K16–K18、K25、**K26** |
| 场景 | `scene` | SceneGoal / CharacterGoal / Conflict / Emotion / Information / Pacing | K02、K03、K05、K16 |
| 叙事分镜 | `shot` | 人物 / 动作 / 镜头 / 时间 / 构图 / 空间 / 道具 / 光线 | K02、K03、K22、K24、**K27–K29** |

**注意**：`continuity` 层**不允许** LLM 介入——它是纯机器校验（K09）。旧文档把「Shot N End = N+1 Start」交给 LLM 比对是本集明确修正的对象。

**已移除 `generation` 层**：**分镜图不做生成评审**（2026-09-19 决策）。影视化链的终点是分镜提示词（`03` §2.2 / `11` §2.2）。提交出图前仍跑 K19–K21 的机器校验（防无效图提交），但**不产生 `ReviewVerdict`**，也不做评审驱动的重生成。

### 2.6 失败与修复路径

```
机器校验失败（K01–K29）
  └─► 回到产出该对象的阶段重做（03 §2.6 max_validate_retry=2）
      └─► 连续 2 次失败 → 停下并输出 ValidationReport

语义评审 FAIL
  └─► CHAPTER_REPAIR：按 RepairRequest（02 §2.6）逐 issue 最小修改
      └─► 重新评审（累计 ≤ max_revisions=3）
          └─► 仍 FAIL → 停下并输出完整 ReviewVerdict

生成失败（V11，可选下游）
  └─► 该镜标记 FAILED，继续其余镜（不阻断整章）；**无评审、无评审驱动的重生成**
```

**「回到产出该对象的阶段重做」在 S12 起是真回路**：`NovelDirector` 在 EXTRACT 与提交门禁之间成环 —— 被 **G2 的机器校验**挡下（`CommitResult::failed_check_ids` 非空）就**重跑 extractor**，并把上一轮的 `checks_describe` 作为「请只修这些问题后重新输出」喂回 user 消息；上限 `03` §2.6 的 `max_validate_retry`（`GenerateChapterRequest::max_validate_retries`，由 `RunLimits::validation_retries` 下发）。**只有机器校验挡下才重做**（G1 评审 / G3 快照 / G4 契约类原因重跑 extractor 不会变好，不浪费调用）；重做后通过 ⇒ **不计入** `failed_check_ids`（否则会误报 S1 停止）。

**修复回执硬要求**（`RepairReceipt`，`02` §2.6）：未解决的 issue **必须显式列出并说明原因**，禁止静默丢弃。

### 2.7 评审器自身的可信度（防「自评全 PASS」）

无人值守下最大的风险是「评审也由同一个模型做，于是它自评通过」。本集要求：

| # | 机制 |
|---|---|
| M1 | `checks_run` 必须列出实际执行的 check_id；**未跑 = 视为未通过**（不允许「默认通过」） |
| M2 | `semantic_only=true` 的结论占比超过阈值（`09` §2.4）时，该章**必须停下等人复核** |
| M3 | 每 N 章（`09` §2.5，默认 10 章）做一次**抽样人工/双模型交叉复核**，差异进 `audit_logs` |
| M4 | `machine_checkable=true` 的 issue 必须由下一版校验器捕获（覆盖率指标 = 已被机器捕获的 machine_checkable issue / 全部） |
| M5 | **评审模型与写作模型不同**（`openaiModelCritic` ≠ `openaiModelWriter`，配置项已存在：`Settings.h:47/48`） |
| M6 | 评审 Prompt 不得包含「请给出通过结论」之类的引导语 |
