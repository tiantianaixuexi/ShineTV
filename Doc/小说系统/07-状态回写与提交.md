# 07 · 状态回写与提交

> 本卷修复本系统最关键的闭环断点：章节生成后**必须**把状态变化写回世界。定义 StateDiff 的生成算法、提交门禁、事务与幂等、快照与回滚、以及在无人值守下 Canon 如何处理。这是不变式 I10 / I11 的实现处。

## 0. 本卷范围与不做什么

**范围**

- 闭环总览：Before → Chapter → After → Diff → Validate → Commit。
- `StateDiff` 的**生成算法**（谁产、从哪读 Before、如何算 After）。
- 提交门禁（评审 PASS + 校验 PASS）与事务、幂等。
- 章级快照与回滚。
- 无人值守下的 Canon 策略（当前需人工确认，与全自动冲突）。
- 冲突处理（状态自相矛盾时的处置）。

**不做**

- 不定义 `StateDiff` 的字段 → `02` §2.5。
- 不定义表结构 → `01`。
- 不定义校验项 → `06` §2.3。
- 不定义阶段顺序 → `03`。

## 1. 现有落点

### 1.1 闭环断点（核心事实）

- `NovelDirector::GenerateChapter` 的 EXTRACT 阶段（`:269-282`）：

```cpp
// 268-282（节选）
auto er = CallLlm("extractor", exUser);
std::string summary = body.substr(0, std::min<std::size_t>(body.size(), 80));
if (er) {
    const auto ej = ExtractOutputText(*er);
    yyjson_doc* doc = yyjson_read(ej.data(), ej.size(), 0);

```

**只取 `summary`**；Prompt 要求输出 `new_entities` / `events` / `foreshadow_updates`（`:123-129`）**全部解析后丢弃**。

- SAVE 阶段（`:285-298`）：
  - `row.status = "review"`（`:289`）——**章节状态停在 `review`，不再推进到 `done`**。
  - `mem.Write({kind:"chapter_summary", …})`（`:293`）。
  - `g.LogAudit("agent","generate_chapter","chapter",…)`（`:297`）。
- **结论：章节生成完全不回写世界状态。**

## 2. 目标设计

### 2.1 闭环总览

```
Before State（读，算哈希）
    ↓
NOVEL_WRITE → chapters.body（PROPOSED，不覆盖 CANON 版本）
    ↓
CHAPTER_REVIEW → ReviewVerdict
    ↓（PASS）
STATE_EXTRACT → StateDiff            ← 本卷 §2.2
    ↓
STATE_VALIDATE → ValidationReport    ← 06 §2.3 的 K01–K29
    ↓（PASS）
SNAPSHOT                             ← 本卷 §2.4
    ↓
COMMIT（事务，唯一有副作用的阶段）    ← 本卷 §2.3
    ↓
After State（重算哈希，写入 work/ch*/_manifest.json）
    ↓
NEXT_CHAPTER
```

**不变式 I10 的落地**：任何一章结束时，`work/ch<NNN>/12_state_diff.json` 必须存在，且 `no_change_declared` 与子数组一致。

### 2.2 `StateDiff` 的生成算法

**产出者**：`STATE_EXTRACT` 阶段的 `extract` Agent（`05` §2.2）。
**输入**：`ChapterPlan` + 正文 + **Before State**（只读，不由 LLM 提供）。

**三步算法**：

| 步 | 名称 | 内容 | 谁做 |
|---|---|---|---|
| ① | **采集 Before** | 按 `01` §2.3.2 取本章涉及实体的「第 N-1 章状态」，作为对照基线，**不由 LLM 叙述** | 代码 |
| ② | **模型提取** | LLM 读正文 + 计划，产出 `StateDiff` 候选（`02` §2.5） | `extract` Agent |
| ③ | **差分校验与补全** | 代码逐条比对：候选与 Before 冲突 → 标记；正文中有明显状态变化但候选未列出 → 标记遗漏 | 代码 |

**③ 的具体规则**（防止 LLM 漏提或幻觉）：

| 规则 | 检查 |
|---|---|
| D1 | `characters[].entity_id` 必须是 Before 或 `entities`（`NewEntity`）中存在的；否则 `code=contract` |
| D2 | `characters[].location_id` 的变化必须能由 `ScenePlan.events` 中的某个事件解释；否则记 `causality_break` |
| D3 | `relationships/items/foreshadows` 的 delta 必须能对应到正文引用（`evidence` 非空）；否则记 `low` |
| D4 | 若 `characters` 中出现 `dead`/`destroyed`，必须同时给出 `entities` 中的 status 变更；否则记 `high` |
| D5 | 若正文出现了**未在 `ChapterPlan.events` 中声明**的新事件，必须补进 `events`；漏则记 `high` |
| D6 | `foreshadows` 的 `status` 迁移必须符合 `01` §2.3.3；反方向即 `high` |
| D7 | `no_change_declared=true` 时所有子数组必须为空（`02` §2.5）；否则 `high` |
| D8 | **`StateDiff` 不得引入 `ChapterPlan` 中未声明的全新角色**（除 `NewEntity` 显式声明） |

**关键设计**：LLM 只负责「从正文里看出变化」，**不负责判断基线**。基线永远由代码从库里读（`01` §2.3.2）。这消除了「模型把状态记错」这一类失败。

### 2.3 提交门禁与事务

**门禁（必须同时满足，缺一不提交）**：

| # | 条件 | 判定者 |
|---|---|---|
| G1 | `ReviewVerdict.verdict == "PASS"` | `06` §2.4 |
| G2 | `ValidationReport` 中 K01–K29 全部 `pass`（`low` 级可记但放行） | `06` §2.3 |
| G3 | 存在 Snapshot（不变式 I11） | §2.4 |
| G4 | `StateDiff` 契约校验通过且非空（或 `no_change_declared=true`） | `02` §2.5 |
| G5 | 无未解决的 `high` issue | `02` §2.6 |

**实现（S10/S11，`src/novel/NovelCommit.cpp`）**：
- **G2 是真门禁**：调用方给 `CommitContext::validation`（`06` §2.3 的报告）就以它为准（`g2_source="caller"`）；**没给则 `CommitChapterState` 自己跑 `RunChapterChecks`**（`g2_source="inline"`，S11 起的默认路径）。不给调用方留"跳过校验"的后门。
- **顺序是硬的**：章级快照必须在 G2 **之前**落盘 —— 否则 K13（`snapshot.before_commit`）没有受检对象（S11 接线时踩实）。
- **失败项并入 G5 与拒绝原因**：报告里 `!CheckPassed` 的条目以 `{check_id + name, severity, detail}` 进 `CommitGateReport::issues`，因此拒绝时可读出「K08 invariant.order_monotonic：…」这种可直接修的信息。
- **把报告交回调用方**：`CommitResult.checks_describe`（一行摘要）+ `failed_check_ids` → `NovelDirector` → `09` §2.2 的 S1 与「回到产出阶段重做」（`03` §2.6）。

**事务边界**：

```
BEGIN;
  1) entities        ← NewEntity[]（先插入，得到真实 id，回填 TempId 映射）
  2) character_status← CharacterDelta[]（INSERT，按章 append）
  3) relations       ← RelationDelta[]（op=close → UPDATE to_chapter；op=upsert → INSERT）
  4) entity_ownerships ← ItemDelta[]（acquire/lose）
  5) event_details + event_participants ← EventDelta[]
  6) causal_links    ← CausalDelta[]（TempId → 真实 id）
  7) foreshadowings  ← ForeshadowDelta[]
  8) mysteries + mystery_beats  ← MysteryDelta[]
  9) plots + plot_beats         ← PlotDelta[]
 10) secret_knowledge / character_knowledge ← KnowledgeDelta[]
 11) chapters        ← body + status='done' + summary + words
 12) entity_versions ← 每个被改实体的新版本快照（ver = max(ver)+1）
 13) canon_logs      ← 本次提交的 Canon 决议（§2.5）
 14) audit_logs      ← 一条汇总记录（actor='agent', action='commit_chapter', detail=DiffSummary）
COMMIT;
```

**顺序要求**：① 必须最先（其余块的 `TempId` 依赖真实 id）；`chapters` 必须最后（它是「本章已完成」的标志）。

**失败处理**：任一步失败 → `ROLLBACK`；`work/` 产物与快照**保留**，供修订后重提。

**幂等（`03` §2.7 P3）**：

| 规则 | 内容 |
|---|---|
| I1 | 提交前检查 `canon_logs` 中是否已存在 `(target_kind='chapter', target_id=chapter_id, status IN ('CANON','PROPOSED'))`；若存在且 `StateDiff` 哈希一致 → **跳过提交**，返回「已提交」 |
| I2 | `character_status` 重复提交时：先删 `(entity_id, chapter_id)` 同键行再插（与 `NovelFields` 同策略） |
| I3 | 重复提交**不得**产生第二条 `audit_logs` 汇总记录（用 `detail` 中的 `diff_hash` 去重） |
| I4 | 部分提交（事务中断）不得留下半成品：因有事务保证，回滚即可 |

### 2.4 快照与回滚

**当前状态**：`entity_versions(id, entity_id, ver, snapshot_json, note, created)` **零 C++ 引用**（`NovelDb.cpp:677`）。

**目标设计**：

| 项 | 决定 |
|---|---|
| **实体级快照** | 每次 Commit 对**被改动的实体**写一行 `entity_versions`（`ver = max(ver)+1`，`snapshot_json` = 该实体相关表的聚合 JSON，`note` = `"ch<N> commit"`） |
| **章级快照** | `<novelRoot>/<书名>/snapshots/ch<NNN>.json`，内容 = 本章 `StateDiff` + 涉及实体的 Before 值 + `input_state_hash` |
| **快照时机** | `COMMIT` 之前（不变式 I11）；写入失败即阻断提交 |
| **回滚粒度** | ① 单章回滚：以章级快照为「反向补丁」；② 实体回滚：按 `entity_versions.ver` 恢复 |
| **回滚的边界** | 回滚**不**自动执行；必须由 `09` §2.2 的停止条件触发并等人工确认（回滚是破坏性操作） |
| **保留策略** | 章级快照永久保留；实体级快照每实体保留最近 `N` 版（`09` §2.4），更早的进冷存档 |

**反向补丁的定义**：对每个 delta 生成对应的「撤销操作」：

| delta 类型 | 撤销 |
|---|---|
| `NewEntity` | 将实体 `status` 置 `archived`（**不物理删除**，避免破坏引用） |
| `CharacterDelta` | 删除该 `(entity_id, chapter_id)` 的 `character_status` 行 |
| `RelationDelta(upsert)` | 若该行由本次创建 → 删除；否则恢复原 `strength`/`reason` |
| `RelationDelta(close)` | 恢复 `to_chapter` 原值 |
| `ItemDelta(acquire)` | 删除对应 `entity_ownerships` 行 |
| `ForeshadowDelta` | 恢复原 `status` |
| 其余 | 按 `entity_versions` 的上一版恢复 |

### 2.5 无人值守下的 Canon 策略（**本集必须给出决定**）

**冲突**：现有设计是「写默认 `PROPOSED`，作者点确认才 `CANON`」（`NovelGraph.cpp:807`、`NovelView.cpp:324-335`）；而目标是**全自动无人值守连写几百章**。若每章都等人点，无人值守不成立。

**决定**：

| 模式 | 规则 | 适用 |
|---|---|---|
| `manual`（默认） | 提交写 `PROPOSED`；等待 UI 确认转 `CANON`；**下一章的 Before State 以 `PROPOSED` 为准**（否则连写无法继续） | 有人在看 |
| `auto` | 提交时直接写 `CANON`，条件：**G1–G5 全部满足** 且 `semantic_only` 占比未超阈值（`06` §2.7 M2） | 无人值守 |

**关键规则**：

| # | 规则 |
|---|---|
| C1 | 无论哪种模式，**章节生成本身的输入始终包含 `PROPOSED` 状态**（否则连写断裂）。`PROPOSED` 表示「未经人审」，不表示「不可用于后续生成」 |
| C2 | `auto` 模式下，每 `09` §2.5 的检查点（默认 10 章）产出一次「人工复核清单」：列出该区间的 `high` issue、被自动升 CANON 的字段定义（`08` §2.3）、`semantic_only` 章 |
| C3 | 人工在任何时候把某章标为 `NON_CANON` → 触发**依赖传播**：沿 `dependencies` 找下游章节，标记「待复查」 |
| C4 | 模式在工程级配置（非全局），且每次运行写入 `audit_logs` |
| C5 | **禁止**在 `auto` 模式下跳过 G1–G5 任一条件直接提交 |

### 2.6 冲突处理

| 冲突 | 检测 | 处置 |
|---|---|---|
| 同一实体同章两个地点 | K07 | 阻断；回 `STATE_EXTRACT` 重提 |
| 已死角色作为行动者 | K04 | 阻断；若正文确实需要（如回忆/幻象），须在 `ChapterPlan` 中显式声明为 `memory`/`illusion` 场景 |
| 伏笔状态回退 | K11 | 阻断；要求 `extract` 说明是「新伏笔」还是「修正历史」；修正历史需人工确认 |
| 因果成环 | K06 | 阻断；删除构成环的最后一条 `causal_link` 并记录 |
| 与已 `CANON` 章节矛盾 | 提交前比对相关实体 `entity_versions` | **不阻断**，但记 `high` 并进复核清单（可能是正常的剧情反转） |
| 快照写入失败 | — | **阻断提交**（不变式 I11） |

**总原则**：冲突一律「阻断 + 记录 + 回到产出该对象的阶段」，**不允许静默修正**（与 `06` §3 的 06-8 差距相呼应）。
