### 第二十三轮顺带挖出、**但本轮不修**的一个真缺陷

`kit::Tree`（`kit/Widget_Tree.cpp:68`）的行 id 是 `"<id>#<depth>##<i>"`，而 `i` 只算
**同一父节点内**的下标，**父节点的下标不在 id 里**。小说侧栏树是「卷 → 章 → 镜」：
**第二卷的第 0 章和第一卷的第 0 章都得到 `side-tree#1##0`**。只要两行同时落在裁剪区内，
ImGui 就报 `Programmer error: 2 visible items with conflicting ID!` 并把两行框红 ——
**后注册的那一行永远拿不到 `HoveredId`，也就是点不动**。

- **不是本轮引入的**：本轮没动 `Widget_Tree.cpp`，`RefreshNovelSideTree` 是逐行搬移，
  树的节点数 / 展开态 / 行 y 一字未变。复现是**间歇的**（是否两行同时可见取决于滚动位置
  与抓到哪一帧），所以它在取证里时有时无：`imageflow-result-shot` 与
  `imageflow-canvas-folded` 两张图在两轮之间 115845 / 115519 像素的差异**完全相同**，
  是那个对话框时有时无，不是位移。
- 本仓已有的 `duplicate-hits` 判据**抓不到它**：那查的是「同帧重叠热区」，
  而这里是「同 id 不同矩形」—— 两条是不同的失效。
- **修法**（下一轮，一行）：id 带上父节点的先序路径，例如
  `snprintf(..., "%.*s#%d##%d", id.size(), id.data(), depth, i)` 改成掺入
  `nodeIndexOfParent`。⚠️ 改 id 会动 `hover-tree-node` 探针的读数，改完必须重跑那一段。

#### 第三轮：审计 #3（`line.*` / `fill.*` 的 alpha）—— 口径错了，不是算法错了

一条**被自己的记录带偏过**的偏差。原口径是「按 `--bg-surface` 摊平成实色，已知偏差，
按明暗顺序判而不是按像素判」。那个口径把问题定性成「只能二选一」——其实不用选：
**底色是画的时候才知道的，就不该在数据层定死**。

- 改法只有一步：5 套主题 JSON 的 `line.*`（五套都是 CSS 原文的 rgba）与
  `fill.*`（只有纸墨/水墨是 rgba）**原样存 8 位 rgba**，由渲染器按实际已画内容做
  source-over 混合。ImGui 本来就是 alpha 混合的，**什么都不用加**。
- 于是不需要给 `DrawRoundRect` 加底色参数，也不需要按底色准备多套 `Derived` 变体 ——
  原先评估的「三层都要改」其实是「只需要改数据层」。
- 改动前逐主题交叉验算五套：旧 JSON 值**恰好等于** `FlattenOver(raw, bg-surface)`
  （逐通道相等）⇒ 落在 `bg-surface` 上的元素视觉不变，改动只影响非 surface 底。
- 实测复核（`out/_colorcount.ps1`，深空 `ws-grid.png`）：旧边色 `#202734` **4902 → 38**，
  新边色 `#29313E` **7 → 3987**，对照组 `bg-panel` 底色 333107 不变。
- 连带影响已核对：`MixSrgb(tone, fillMuted, N)` 在浅色两套下结果**带 alpha** ——
  那是 CSS `color-mix` 的答案（≈0.14），不是 bug。
- 新增工具 `out/_colorcount.ps1`：`_pixdiff` 只说「差了多少像素」，不说「变成了什么色」，
  而这个空档正是「算式算出来了、但没人验过真到没到像素」长期混过去的地方。

### 字形只有请求字号的 **0.76 倍**（第十一轮查出 → **第十七轮已修**，全仓级）

> ⚠️ **本节第十一轮记的候选公式是反的**，第十七轮按源码核对后订正并实修：
> `imgui_draw.cpp:4747` 把 `ExtraSizeScale` **乘**进 `ScaleFactor`，而字形位图与
> AdvanceX 按 `ScaleFactor × baked->Size` 算（:4801，**不再除回**）⇒ 字形与步进 ∝ E。
> 所以正确值是 **E = (A−D)/upem ≈ 1.32**（放大），不是 upem/(A−D) = 0.7577（那是缩小）。
> 行高度量（Ascent/Descent，:4780）除回 E **保持不变** ⇒ 基线体系不动，只有墨迹变大。

**现象**：`FontAt(x)` / `FontBoldAt(x)` 画出来的 CJK，em 盒**不是 x px**，而是 **0.758 × x**。

**证据链（源码 + 实测都有，互相印证）**：

- `third/imgui/imgui_draw.cpp:4801`：`scale_for_layout = ScaleFactor * baked->Size`，
  而 `:4744` 的 `ScaleFactor = stbtt_ScaleForPixelHeight(FontInfo, 1.0f)`。
- `third/imgui/imstb_truetype.h:2665-2669` 写着这支函数的定义就是
  `height / (hhea.ascent − hhea.descent)` —— 即 **ImGui 的「字号」＝把 A−D 这个跨度
  映射成那么多像素**，而 CSS 的 `font-size` 是 **em 盒**。msyh 的 A−D ≈ 1.32 em
  ⇒ 2048/2703 = **0.7577**。
- 实测（`build/shots-r11/overview-bound.png`）：KPI 数值请求 **24px**，墨迹宽 **54px**
  （3 个全角字，即每字 18px = 0.75 × 24）；标签请求 11.5px，墨迹宽 34px（4 字，每字 8.5px）。
- **对照**：同一段 CSS 在 Chrome 里（探针页 canvas）`未接入` 在 24px 下宽 **72px**（每字 24px）、
  `阶段进度` 在 11.5px 下宽 **46px**。⇒ 我们的字比设计稿**小 24%**。

**为什么一直没被发现**：所有字号**一起**小 24%，图标/间距/盒子是另一套（不受影响），
于是「排版整体偏紧」读起来像风格，不像缺陷；而设计稿的对照图不在版本控制里（`webui/`），
逐轮比对时没有并排的基准。

**候选修法（未验证，单独一轮做）**：`ImFontConfig::ExtraSizeScale = upem/(A−D)`
（它正是 `scale_for_layout` 的除数，`imgui_draw.cpp:4780`），即让 em 盒映射到请求字号。
⚠️ 注意三件事：① 它**逐字体**不同（msyh / 宋体 / Cascadia 各一个比值）；
② `baked->Size` 不变 ⇒ `scale = size/baked->Size` 恒为 1，**排版量（行盒 = size）不变**，
只有字形与步进变大；③ 因此它会**同时**改变每个字的步进（宽度 +32%）⇒
所有按 CSS 算出来的横向排布（标签、按钮、KPI 脚注、表格列）都要重核一遍，
是**多轮的量级**，不要和别的改动混在一起。

⚠️ 在修之前，凡是「按 CSS 行盒算位置」的自绘文字（这一轮的 KPI 卡就是这样）：
**基线与设计稿对齐**仍然是对的，别指望墨迹位置也对齐。
